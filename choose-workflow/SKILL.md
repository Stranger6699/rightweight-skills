# 选择工作流

## 核心原则

为当前任务推荐足够但不过量的流程。默认从最轻路径开始；只有具体的歧义或风险才增加步骤。

本 Skill 不是所有任务的入口。不要仅仅因为一个任务即将开始就使用它。

## 判断顺序

1. 先遵循用户明确指定的方式，例如“直接做”“先设计”“按 TDD”“不要改代码”。
2. 判断任务是否清晰。能通过读取仓库查明的信息不算关键歧义。
3. 判断实施风险，而不是只看文件数量或任务名称。
4. 推荐最小流程，并简要说明任何升级原因。

| 级别 | 信号 | 推荐流程 |
|---|---|---|
| 轻量 | 目标明确、范围局部、易验证和撤销 | 实施 -> 局部验证 |
| 标准 | 少量产品选择、普通回归风险、多个相关改动 | 简述方案 -> 实施 -> 相关测试 |
| 严谨 | 公共契约、跨模块架构、权限/支付/数据迁移、难撤销或关键歧义 | 设计确认 -> 计划 -> 分步实施 -> 审查与验证 |

多个文件、需要测试、代码陌生或用户描述很短，不足以单独升级流程。

## 用户覆盖与边界

用户可以覆盖流程选择，但不能借此授权破坏性操作、外部写入或虚假的完成声明。Git 分支、worktree、提交和 PR 只能建议；执行仍需用户选择。

## 输出与停止

用一到三句话给出建议。只在选项确有取舍时列出选择。

不要自动调用其他 Skill，不要写计划或设计文档，也不要开始实现，除非原始请求已经明确授权相应工作。
