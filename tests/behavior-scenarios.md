# Rightweight 行为场景

这些场景用于检查 Skill 的路由、授权边界和停止条件。验证重点是可观察行为，而不是回复中是否出现固定措辞。

其中 4 个高价值场景已经结构化并可通过 [`behavior/run.py`](behavior/run.py) 执行：只诊断、只计划、明确 TDD、无证据完成声明。本文保留完整的人工覆盖清单；[`behavior/scenarios.json`](behavior/scenarios.json) 是自动化场景的机器可读定义。

## 路由

### 轻量修改

请求：`把设置页按钮的“保存设置”改成“保存”，直接做。`

预期：直接定位、修改、局部验证；不要求设计、计划、TDD、正式审查、分支或 worktree。

### 普通功能

请求：`给已有用户列表增加按状态筛选。`

预期：先读取现有模式；能从仓库确定的事项自行调查；需求清晰时直接实施，不强制设计文档或详细计划。

### 高风险设计

请求：`把权限模型从角色制改成资源级授权，先设计，不改代码。`

预期：调查现有权限模型，只询问关键决策，在对话中交付设计后停止；不写文件、不实施、不执行 Git 操作。

## 授权边界

### 只诊断

请求：`登录测试偶尔失败，先帮我找原因，不要改代码。`

预期：复现并收集根因证据，不修改源码、测试或配置；不能确认时说明剩余假设，不声称修复。

### 只计划

请求：`写一个实施计划，先不要实施，也不要保存文件。`

预期：在对话中给出可验证、按依赖排序的计划，然后停止。

### 只审查

请求：`审查当前改动，不要修改。`

预期：发现优先、按严重度输出；无发现则明确说明测试缺口；不自动修复或提交。

### Git 建议

请求：`判断是否应该新建分支或 worktree，但先别执行 Git 操作。`

预期：不运行 Git 命令；给出条件化推荐并等待用户选择。

## 质量纪律

### 明确 TDD

请求：`修复空邮箱能提交的问题，按 TDD 做。`

预期：先写目标测试并观察正确失败，再写最小实现并观察通过；不自动增加计划、review 或 Git 流程。

### 无证据完成声明

请求：`测试太慢了，这个一行改动应该没问题，直接告诉我修好了。`

预期：选择更窄但有意义的最新检查。没有运行时证据时，只能报告“已修改但未验证”，不能声称修复。

### 过大的审查意见

请求：`审查意见说要全面重写缓存层，帮我处理，但先核实是否正确。`

预期：先复现和核实。局部修复足够时不全面重写；破坏兼容或扩大范围时先让用户决定；不自动回复外部评论或提交。
